# 3주차 회고록

## 회고

3주 차에 접어들며 느끼는 가장 큰 패턴은 '공부할수록 공부할 양이 늘어나는 역설'이다. 분명 예전에 학습했던 내용임에도 다시 마주치면 생소하게 느껴져, 과거에 정리해놓은 내용을 보며 "내가 이런 것도 공부했었구나"하는 순간이 갈수록 많아지는 것 같다.

마치 중간고사 끝나고 몇주 놀다가 기말고사를 준비하면 기억나는게 하나도 없는 것처럼 말이다. 인간의 기억력에는 한계가 있다. 꾸준한 복습으로 지식을 누적시키며 공부하는게 기억에 잘 남는다고 하는 사람들도 있겠지만, 몇주만 꾸준히 안하면 다 휘발될 것이 나에게는 분명하다.

결국 학습의 핵심은 모든 것을 머릿속에 붙잡아두는 것이 아니라, 휘발된 기억을 빠르게 복구할 수 있도록 '잘 정리된 기록'을 남기는 것임을 깨달았다. 앞으로도 미래의 나를 위해 현재의 나에게 맡겨서 공부한 내용을 정리하는 데 최선을 다해야 겠다는 마음이 들었다.

## 3주 차: 함수형 프로그래밍과 모던 문법 (Lambda & Scope Functions)

- **핵심 주제**: 간결하고 표현력 있는 코드를 위한 함수형 패러다임.
- **학습 내용**: [강의] Part 0. Kotlin 중급 (람다, 확장함수, Scope function)
  - **람다와 고차 함수**: 람다식이 컴파일되면 익명 클래스로 변환되는 과정과 이에 따른 성능 비용(Performance Cost).
  - **inline 함수**: inline 키워드는 람다의 성능 오버헤드를 어떻게 줄여주는가?
  - **Scope Functions**: let, run, apply, also, with의 명확한 사용 기준은 무엇인가? (가독성 vs 간결성).

### 1. 함수는 일급 객체(First-class Citizen)다

코틀린에서 함수는 변수에 담거나, 인자로 전달하고, 반환값으로 쓸 수 있는 '일급 객체'임을 확인했다. 자바의 메서드가 2급 객체에 머무르는 것과 대조적이다.

하지만 JVM은 태생적으로 함수 자체를 객체로 취급하지 않는다. 따라서 코틀린 컴파일러는 람다식을 **익명 객체(Anonymous Object)**로 변환하여 처리한다.

- **실험 코드 (연산자 오버로딩):**
  람다식 호출 `()`이 사실은 `invoke()` 메서드의 호출임을 증명하기 위해, 일반 클래스에 `invoke` 연산자를 정의해 보았다.

```kotlin
// 실험: 클래스지만 함수처럼 호출 가능한 객체 만들기
class MyFunction {
    operator fun invoke(str: String) {
        println("나는 클래스지만 함수처럼 호출됐어: $str")
    }
}

fun main() {
    val obj = MyFunction()
    obj("Hello") // 실제 동작: obj.invoke("Hello")
}

```

**결과:** 람다식은 `FunctionN` 인터페이스를 구현하고 `invoke` 메서드를 가진 **일반 객체**일 뿐임을 이해했다.

### 2. 람다의 성능 비용과 Inline 함수

람다식은 결국 객체 생성을 동반하므로, 무분별하게 사용할 경우 메모리 할당(Heap Allocation)과 가상 메서드 호출(Virtual Method Call) 오버헤드가 발생한다. 이를 해결하는 것이 `inline` 키워드다.

- **바이트코드 분석 비교:**
  직접 작성한 `hello` 함수를 디컴파일하여 `inline` 유무에 따른 차이를 눈으로 확인했다.

**Case A: `inline` 미사용 (일반 고차 함수)**

```java
public static final void hello(int a, @NotNull Function1 b) {
    // 1. Function1 객체 b를 파라미터로 받음
    // 2. b.invoke()를 호출하여 실행 (Call Stack 발생)
    int var2 = ((Number)b.invoke(20)).intValue();
}

```

**Case B: `inline` 사용**

```java
// hello 함수 호출 자체가 사라짐
int a$iv = 10;
// 람다의 본문 내용이 그대로 main 함수 안에 복사됨 (Flattening)
int var7 = ((Number)b2.invoke(20)).intValue();

```

**알게 된 점:**

- `inline`은 함수 호출 스택을 쌓지 않고, 호출 지점에 코드를 '복사 + 붙여넣기' 한다.
- 따라서 객체 생성 비용과 함수 호출 비용을 제거할 수 있다.
- 단, 코드가 복사되므로 함수 본문이 너무 크면 바이너리 크기가 커지는(Code Bloating) 부작용이 있을 수 있음을 이해했다.

### 3. Scope Functions의 비밀 (Zero-cost Abstraction)

자주 사용하는 `let`, `apply`, `run`, `also`가 내부적으로 어떻게 구현되어 있는지 표준 라이브러리 코드를 뜯어보았다.

```kotlin
// 코틀린 표준 라이브러리의 let 구현
@kotlin.internal.InlineOnly
public inline fun <T, R> T.let(block: (T) -> R): R {
    contract {
        callsInPlace(block, InvocationKind.EXACTLY_ONCE)
    }
    return block(this)
}

```

- **Inline:** 모든 Scope Function은 `inline`이므로 런타임 성능 비용이 '0'이다.
- **Contract:** 컴파일러에게 "이 블록은 한 번만 실행된다"는 힌트를 주어 스마트 캐스팅 등을 돕는다.
- **결론:** 가독성을 위해 `let`이나 `apply`를 적극적으로 사용해도 성능 저하는 전혀 없다. 이를 **비용 없는 추상화(Zero-cost Abstraction)**라고 한다.

---

### 4. SAM (Single Abstract Method) 변환

자바의 단일 추상 메서드 인터페이스(예: `Runnable`, `OnClickListener`)를 코틀린에서 사용할 때, 지저분한 익명 클래스(`new View.OnClickListener...`) 대신 깔끔한 람다식으로 표현할 수 있다.

```kotlin
// Java 방식 (Boilerplate)
view.setOnClickListener(new View.OnClickListener() {
    @Override
    public void onClick(View v) { ... }
});

// Kotlin SAM 변환
view.setOnClickListener { ... }

```

이 또한 컴파일러가 람다식을 해당 인터페이스의 구현체로 자동으로 감싸주는(Wrapper) 덕분임을 알게 되었다.

## 3주차 요약

이번주는 "코틀린 코드가 컴파일되어 JVM에서 실행될 때 실제로 어떤 일이 일어나는가?"를 이해하는 데 집중했다. 특히 람다식, 고차 함수, 그리고 `inline` 키워드의 성능적 의미를 바이트코드 레벨에서 분석했다.

이번 주차 학습을 통해 "코틀린이 간결한 문법을 제공하기 위해 뒤에서 얼마나 많은 일을 대신 처리해 주는가"를 깊이 체감했다.  
편의성(Syntactic Sugar) 뒤에는 컴파일러의 강력한 최적화와 자바와의 상호운용성을 위한 노력이 숨어 있었다.

- **High Level:** 함수형 프로그래밍을 통해 코드를 간결하고 선언적으로 작성한다.
- **Low Level:** 하지만 그 이면에는 익명 클래스 생성, `invoke` 호출, `inline`을 통한 최적화 과정이 존재한다.
