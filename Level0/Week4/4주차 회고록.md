# 4주차 회고록

## 회고

처음 레벨 0 과정을 시작할 때는 4주 동안 무엇을, 어떻게 공부해야 할지 감을 잡지 못해 막막했다.

평소의 나는 무언가를 공부하기 전에, 다람쥐가 도토리를 모으듯 온갖 학습 자료부터 닥치는 대로 수집하는 습관이 있었다. 완벽하게 준비한 상태에서 시작하려다 보니 정작 제대로 된 공부는 시작조차 하지 못하는 악순환을 겪곤 했다.

하지만 이번 4주간의 레벨 0 과정을 통해 주차별로 명확히 무엇을 어떻게 언제까지 마쳐야 하는지가 구체적으로 계획을 세울 수 있었다. 명확한 제약과 방법이 게으른 나의 실행력을 예전보다 키워주었다고 생각된다.

즉, 이번 4주간의 경험을 통해 **'완벽한 자료 수집'보다 '명확한 목표와 기한 설정'이 실제 성장을 이끈다**는 것을 느꼈다. 본 과정에 들어가서도 자료 수집에 매몰되는 예전 습관을 버리고, 이번에 확립한 '목표 지향적이고 기한을 지키는' 학습 리듬을 계속 유지해야겠다고 다짐했다.

## 4주 차 학습내용

### 1. 4대 컴포넌트 (앱 구성요소)와 Manifest, Intent

전통적인 데스크톱 애플리케이션이나 백엔드 서버와 달리, 안드로이드는 고유한 생명주기와 진입점을 갖는다.  
구글이 왜 이러한 아키텍처를 설계했는지 생각해보고자 한다.

안드로이드 앱은 C, C++, Java, Python처럼 프로그램의 시작을 알리는 단일 메인 함수로 구동되는 구조가 아니다. 시스템이나 사용자가 필요할 때 앱의 특정 부분을 독립적으로 인스턴스화하여 실행할 수 있도록 설계된 다중 진입점 시스템이다.

#### Activity

사용자와 상호작용하는 UI 화면을 담당하는 진입점이다. 하나의 화면은 보통 하나의 Activity로 구성된다. 앱이 포그라운드에 있을 때 OS가 메모리와 자원을 할당하고 생명주기를 직접 관리한다.
이는 데스크톱 앱의 윈도우 객체와 유사해 보이지만, 모바일 환경의 제한된 메모리 특성상 언제든 OS에 의해 백그라운드에서 강제 종료되고 재생성될 수 있다는 점이 핵심이다. 화면 회전이나 메모리 부족 상황에서 뷰의 상태를 어떻게 보존할 것인지 고민하게 만드는 주된 원인이기도 하다.

#### Service

사용자 인터페이스 없이 백그라운드에서 오래 실행되는 작업을 수행하는 컴포넌트이다.
C나 C++의 데몬 프로세스, Python의 백그라운드 스레드와 목적은 비슷하다. 하지만 스레드는 앱 프로세스가 종료되면 함께 사라지는 반면, Service는 안드로이드 시스템에 의해 그 자체로 생명주기를 부여받아 프로세스의 우선순위에 영향을 미친다. 음악 재생이나 대용량 파일 다운로드처럼 앱 화면이 전환되거나 종료되어도 지속되어야 하는 작업에 활용된다.

#### Content Provider

애플리케이션 간에 데이터를 공유하기 위한 표준 인터페이스이다.
안드로이드는 보안상 앱마다 샌드박스라는 독립적인 실행 환경과 고유한 리눅스 사용자 ID를 부여하므로, 다른 앱의 내부 데이터에 직접 접근할 수 없다. Content Provider는 이를 해결하기 위해 OS 레벨에서 제공하는 안전한 프로세스 간 통신(IPC) 채널이다. 내부적으로는 SQLite 데이터베이스를 주로 사용하며, 웹 서비스의 REST API가 가진 철학을 모바일 기기의 로컬 환경에 구현한 것으로 볼 수 있다.

#### Broadcast Receiver

안드로이드 OS나 다른 앱에서 발생하는 시스템 전역적인 브로드캐스트 메시지를 수신하고 응답하는 컴포넌트이다.
배터리 부족, 화면 꺼짐, 네트워크 상태 변경 등의 이벤트가 발생할 때 동작한다. 소프트웨어 공학의 발행-구독(Pub-Sub) 패턴을 운영체제 수준으로 확장한 개념으로, 앱이 메모리에 상주하여 실행 중인 상태가 아니더라도 시스템 이벤트를 감지하여 특정 로직을 안전하게 트리거할 수 있게 해준다.

---

#### Manifest

앱의 설계도 역할을 하는 XML 기반의 명세서이다.
프로그램을 컴파일할 때 C나 C++에서 링커가 심볼 테이블을 참조하여 실행 파일의 구조를 엮는 것처럼, 안드로이드는 런타임 이전에 Manifest를 통해 앱의 구조를 시스템 환경에 등록한다. 안드로이드는 다중 진입점 메커니즘을 사용하므로, OS는 앱 프로세스를 메모리에 적재하기 전에 앱이 어떤 컴포넌트를 가지고 있는지, 어떤 하드웨어 권한이 필요한지 완벽하게 파악해야 한다. 이곳에 명시되지 않은 컴포넌트는 시스템이 결코 인스턴스화할 수 없다.

#### Intent

안드로이드 컴포넌트 간의 통신을 담당하는 비동기 메시지 객체이다.
메모리 주소를 직접 참조하거나 소켓 통신을 기반으로 하는 C나 C++의 저수준 IPC 방식과 달리, Intent는 '무엇을 할 것인가'라는 추상적인 의도를 운영체제에 전달하는 고수준의 방식을 취한다.
명시적 인텐트는 실행할 대상 컴포넌트의 클래스 이름을 정확히 지정하여 내부 이동에 사용되며, 암시적 인텐트는 수행할 작업의 종류만 정의하고 OS가 이를 처리할 수 있는 적절한 타 앱의 컴포넌트를 찾도록 위임한다. 이는 컴포넌트 간의 결합도를 극한으로 낮추고 플랫폼의 유연성을 극대화하는 안드로이드 설계 철학의 결정체이다.

### 2. Activity의 Lifecycle

![Untitled](https://user-images.githubusercontent.com/24618293/204137047-50113f27-3a2d-41c4-9eb9-fd6a8809ecdc.png)

안드로이드 컴포넌트의 생명주기는 제한된 자원을 가진 모바일 기기 환경에서 OS가 애플리케이션의 메모리와 상태를 어떻게 관리하는지 보여주는 핵심적인 설계이다.

데스크톱 환경의 C, C++ 프로그램이나 백엔드의 Java, Python 서버는 보통 메인 함수(main)를 시작으로 개발자가 프로세스의 흐름을 직접 제어한다. 반면 안드로이드는 시스템 환경 변화(배터리 상태, 메모리 부족, 화면 전환 등)에 따라 OS가 앱 구성 요소의 생성과 소멸을 강제하는 **제어의 역전(IoC) 패턴**을 따른다.

런타임 관점에서 왜 구글이 이러한 콜백 구조를 강제했는지 분석해 보자.

#### 2.1. 생명주기 콜백의 존재 이유와 시스템적 역할

안드로이드 OS는 화면의 가시성(Visibility)과 사용자 상호작용(Focus) 유무에 따라 프로세스의 중요도를 평가하고 자원을 할당한다. 각 콜백은 이러한 상태가 변하는 경계선에서 호출된다.

- 인스턴스 메모리 관리 구역
  - onCreate: OS가 Activity 객체를 메모리에 할당하고 뷰 계층 구조를 팽창(Inflate)시키는 최초 진입점이다. 화면 회전 등으로 인해 OS가 프로세스를 죽였다가 재생성할 때, 이전 상태를 복원하기 위해 saveInstanceState(Bundle 객체)가 전달된다. 모든 초기화 로직은 이곳에 집중된다.
  - onDestroy: 시스템 리소스 회수를 위해 객체를 메모리에서 완전히 해제하기 직전에 호출된다. 메모리 누수를 방지하기 위해 백그라운드 스레드나 리스너를 명시적으로 정리해야 하는 위치이다.
- 화면 가시성 제어 구역
  - onStart: 화면이 사용자에게 보이기 시작하지만, 아직 조작은 불가능한 상태이다. 애니메이션이나 UI 업데이트 등을 준비하기 적합하다.
  - onStop: 다른 화면에 의해 100% 가려지거나 앱이 백그라운드로 내려가 더 이상 보이지 않는 상태이다. 이때부터 시스템은 메모리 부족 시 해당 프로세스를 우선적으로 강제 종료(Kill)할 수 있는 권한을 얻는다. 데이터베이스 저장 등 CPU 부하가 크고 시간이 걸리는 종료 작업은 이곳에서 안전하게 처리해야 한다.
- 사용자 상호작용 제어 구역
  - onResume: 화면이 최상단에 올라와 사용자의 입력을 독점적으로 받을 수 있는 상태이다.
  - onPause: 화면의 일부가 가려지거나, 포커스를 잃는 첫 번째 신호이다. 이 콜백의 실행이 완료되어야만 OS가 다음 Activity를 화면에 띄울 수 있다. 따라서 이곳에서 네트워크 요청이나 DB I/O 같은 무거운 작업을 수행하면 스레드가 블로킹되어 앱의 화면 전환이 버벅거리는 현상(ANR)이 발생한다. 빠르고 가벼운 정리만 수행해야 하는 이유가 여기에 있다.

#### 2.2. 테스트 시나리오에 따른 OS 상태 머신 동작 분석 (ex1 예제코드 참고)

1. Activity 종료 시 (뒤로 가기 또는 finish 호출)
   사용자와의 상호작용이 끊어지고(onPause), 화면에서 완전히 사라지며(onStop), 최종적으로 객체가 메모리에서 파괴된다(onDestroy).
2. 다른 앱 실행 시 (홈 버튼 클릭 등)
   앱이 백그라운드로 밀려난다. 포커스를 잃고(onPause), 화면에서 가려진다(onStop). 이때 앱은 메모리에서 즉시 파괴되는 것이 아니라 백그라운드 상태로 캐시 메모리에 머무른다. 사용자가 다시 돌아왔을 때 빠른 복원(onStart -> onResume)을 위함이다. 단, 시스템 리소스가 부족해지면 OS는 onStop 상태의 프로세스를 예고 없이 죽일 수 있다.
3. 다른 Activity 실행 시 (MainActivity에서 NextActivity로 이동)
   시스템은 화면 전환의 부드러움을 위해 두 컴포넌트의 상태를 교차시킨다.
   - 먼저 기존 화면(MainActivity)이 포커스를 잃는다 (onPause).
   - 그다음 새로운 화면(NextActivity)이 메모리에 적재되고(onCreate), 화면에 보이며(onStart), 포커스를 얻는다(onResume).
   - 새로운 화면이 화면을 완전히 덮은 후에야 비로소 기존 화면(MainActivity)이 시야에서 사라졌다고 판단하여 상태를 전환한다 (onStop).

#### 2.3. 결론

이러한 다단계 상태 머신 구조는 모바일 환경의 하드웨어적 한계를 소프트웨어적으로 극복하기 위한 안드로이드의 철학이다. 사용자가 앱을 떠났을 때 시스템 리소스 소모를 막으면서도(onStop 활용), 다시 돌아왔을 때 끊김 없는 경험을 제공하기 위해 상태를 보존(onCreate의 Bundle 등)해야 하는 책임은 온전히 개발자에게 주어진다.

#### 3.2. View 렌더링의 3단계 파이프라인

프레임워크는 화면을 그리기 위해 `Measure` -> `Layout` -> `Draw` 라는 엄격한 순서를 강제한다.

**Measure (크기 측정과 협상)**
각 뷰가 화면에서 차지할 크기를 결정하는 단계다. 안드로이드의 화면 크기는 기기마다 파편화되어 있으므로, 절대적인 픽셀 값보다는 부모와 자식 간의 상대적인 크기 협상이 필수적이다.

- 자식 뷰는 `LayoutParams`를 통해 자신이 원하는 크기(Match_Parent, Wrap_Content 등)를 부모에게 어필한다.
- 부모 뷰는 자신이 가진 물리적 공간의 한계 내에서 `MeasureSpecs`를 생성하여 자식에게 허용 가능한 최대 크기(At_Most)나 정확한 크기(Exactly)를 통보한다.

**Layout (위치 배치)**
크기가 결정되면 부모 뷰는 자식 뷰들을 자신의 영역 내 어디에 배치할지 결정한다. Left, Top, Right, Bottom의 상대 좌표가 이 단계에서 확정된다.

**Draw (픽셀 렌더링)**
결정된 크기와 위치를 바탕으로 `Canvas`(도화지 역할)와 `Paint`(붓과 물감 역할) 객체를 사용해 실제 그래픽을 그리는 단계다.

#### 3.3. JVM 런타임 환경과 onDraw의 성능 제약

C나 C++과 같이 개발자가 메모리를 직접 해제하는 환경과 달리, 안드로이드(Kotlin/Java)는 JVM 기반의 가비지 컬렉터(GC)에 메모리 관리를 위임한다.

사용자가 화면을 스크롤하거나 애니메이션이 실행될 때 `onDraw`는 1초에 60번(60fps) 이상 호출될 수 있다. 만약 이 콜백 내부에서 객체를 새로 생성(할당)한다면, 순식간에 수많은 가비지 객체가 힙 메모리에 쌓이게 된다. 이는 GC의 빈번한 동작을 유발하고, GC가 실행되는 동안 애플리케이션 스레드가 일시 정지(Stop-the-world)되어 화면이 버벅거리는 프레임 드랍(Jank) 현상을 초래한다. 따라서 `onDraw` 내부에서는 객체 생성을 엄격히 금지하고, 뷰 초기화 단계에서 미리 생성해 둔 객체를 재사용하는 것이 프레임워크의 권장 사항이다.

#### 3.4. 상태 변경에 따른 런타임 View 갱신 (예제 코드 분석)

ex2/`MainActivity.kt`의 코드는 런타임에 뷰의 상태가 변했을 때 렌더링 파이프라인이 어떻게 최적화되어 동작하는지 명확히 보여준다.

- **invalidate (부분 갱신)**
  버튼 클릭 시 `setTextColor`를 통해 텍스트의 색상만 변경한다. 색상 변화는 뷰의 물리적인 크기나 위치에 영향을 주지 않는다. 따라서 시스템은 비용이 큰 Measure와 Layout 단계를 생략하고, `onDraw`만 다시 호출하여 화면을 빠르게 갱신한다.
- **requestLayout (전면 갱신)**
  롱 클릭 시 `text = "test"`로 텍스트 내용 자체를 변경한다. 글자가 바뀌면 CustomTextView가 차지해야 할 가로/세로 길이(Wrap_Content 적용 시)가 달라질 수 있다. 자식 뷰의 크기가 변하면 부모 뷰(CustomLinearLayout) 내의 다른 요소들 위치까지 연쇄적으로 재계산해야 하므로, Measure부터 Layout, Draw까지 전체 파이프라인을 처음부터 다시 실행하게 된다.

#### 결론

안드로이드의 기존 View 시스템은 이처럼 뷰의 상태가 변할 때마다 개발자가 속성을 직접 변경하고 `invalidate`나 `requestLayout` 같은 갱신 함수를 암묵적 혹은 명시적으로 호출해야 하는 명령형(Imperative) 접근 방식을 취한다. 이는 상태와 UI의 동기화가 조금만 어긋나도 버그로 직결되는 원인이 되었다.

## 4주차 요약

이번 주차에는 안드로이드 OS의 기본 동작 원리와 뷰 시스템을 학습하며, 단순히 화면을 그리는 것을 넘어 모바일 플랫폼의 근본적인 설계 철학을 고민해 보았다.

- **다중 진입점(Multiple Entry Points)과 제어의 역전(IoC):**
  기존에 익숙했던 C나 Java 프로그램은 `main()` 함수라는 단일 진입점을 통해 실행의 주도권을 개발자가 가졌다. 하지만 안드로이드는 모바일 환경의 특성(화면 전환, 알림, 백그라운드 작업 등)상 다중 진입점(Activity, Service 등) 구조가 필연적임을 이해했다. 이로 인해 생명주기 관리를 운영체제(OS)가 전담하게 되면서 발생하는 '제어의 역전' 현상을 어떻게 코드 설계로 극복해야 하는지 깨달았다.
- **메모리 부족과 상태 보존(State Preservation):**
  안드로이드 OS는 메모리가 부족할 때 백그라운드 프로세스를 예고 없이 종료(Process Death)시킬 수 있다. 따라서 통제권이 내가 아닌 운영체제에 있는 환경에서는 견고한 소프트웨어를 작성하는 것이 핵심이다. 뷰의 상태나 사용자가 입력 중이던 데이터를 `onSaveInstanceState`나 `ViewModel` 등을 통해 안전하게 보존하고 복원하는 설계 레벨의 고민이 필수적임을 알게 되었다.
- **Context와 메모리 누수(Memory Leak):**
  Context는 안드로이드 시스템(OS)에 접근하기 위한 매개체다. Activity가 소멸(Destroy)되어 가비지 컬렉터(GC)의 수거 대상이 되어야 함에도, 백그라운드 스레드 등에서 해당 Activity의 Context를 계속 참조하고 있다면 메모리 누수가 발생한다는 사실을 명확히 이해했다.
